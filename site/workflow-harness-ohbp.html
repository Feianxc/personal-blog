OHBP / harnessbench：先让材料先放齐，再谈榜单

这一轮只盯四个对象：OHBP v0.1、运行清单 manifest.json、最终材料包 final bundle、verification_record verification_record。

这里不写空口的强弱判断。先让运行命令留下材料，打包命令生成规范材料包，校验命令限定检查说法，verifier再给出结论。没有材料包，就像没有原始文件的测试，名字再亮也无法定位。

价值不在网页上多几个榜，而在执行、打包、验证、结论四件事被分开。

清单先于榜单

评测项目很容易变成一张只有结果分的表：谁跑的、怎么跑的、有没有多次挑最好、有没有人工修补、环境有没有影响，都会藏在摘要分背后。所以这一类先反过来做：不急着把榜单做满，先把协议对象、文件约定和verifier结论写清楚。

这几个对象不能混在一起

对象现在放在哪为什么不能少
协议来源docs/ohbp-v0.1/ohbp-v0.1.md它定义基准卡、任务包、运行清单、材料包、完整性证明和verification_record，不让产品页先替协议做主。
实施蓝图docs/implementation/build-blueprint.md它把执行顺序钉成 A 到 F 六个阶段，而不是一边做网页一边猜协议。
共享包来源packages/schema / canonical / validator-core / verifier-core协议定义不落在界面，也不落在命令行；这样不同入口消费的是同一组规则。
应用入口apps/hb-cli / mock-intake / verifier-worker / web命令行、上传、结论、展示各自负责一段，避免一个应用既当裁判又当选手。
结论对象manifest.json / verification_record运行清单是材料包侧的连接面；verification_record才是平台结论来源。

原始工作区到榜单之前要过几道门

hb inithb runhb packhb validatehb inspecthb upload --dry-run
hb run       只收集原始输出
hb pack      把原始工作区收住成最终材料包
hb validate  只做确定性检查
hb upload    先走模拟接收入口
verifier      生成上传记录 / 完整性证明 / verification_record
web           只消费榜单 / 条目派生视图

这里的关键不是命令多，而是每个命令被限制住了。运行命令不能越界当裁判，网页也不能替verifier下结论。

材料：协议、材料包、校验记录

OHBP v0.1 已经冻结为协议稿

协议文档明确写着“先保留原始材料，再看分数；先定协议，再做产品页”。这句话把项目从页面需求文档拉回到了可审计对象范围。

单体仓结构先把来源拆开

apps/ 和 packages/ 的范围已经写进蓝图：结构定义、规范化、类型、校验器、verifier、页面视图都是单独职责，不允许网页直接持有全部定义。

运行清单被定义成唯一连接面

注册信息、容差策略、可重复性、材料通道和摘要值都只能经 manifest.json 进入消费层。这个限制比“多做一个上传页”更重要。

榜单只是最后一层派生视图

官方验证榜、可复现前沿、社区实验室都是网页最小版本的消费层。它们可以展示结论，但不能替代结论生成。

范围：榜单先不急着扩展

这次不做什么

  • 不定义唯一全球总榜。
  • 不把运营积分和奖励规则固定进协议。
  • 不让命令行、网页或某个页面单独拥有协议定义。

后续对象

  • packages/schema 与 fixtures：goldens / mutants 回归。
  • hb pack：规范化范围。
  • 榜单视觉和条目页面放在协议、材料包、verifier稳定之后。

评测系统先问“这份材料能不能被别人复核”，再问“谁第一”。
