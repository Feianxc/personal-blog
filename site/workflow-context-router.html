skill routing / context budget / governance

Context Router V1：只标出来路线，不替人接管方向盘

V1 的规矩很朴素：能力目录常驻，正文按需加载，attach 只对当前 session 生效。

能力路由最怕变成新的黑箱。一句话切 skill、开 MCP、换插件，短期很炫，长期会污染上下文。Lite 版只做一件事：把能力为什么进场、什么时候退场说清楚，不装作替人决定方向。

2026-04-23 整理router / bundle / governancesuggest + attach + route-log

V1 只保 4 件事

Catalog统一登记 skill / MCP / plugin / CLI
Router根据意图、项目指纹和上下文预算建议能力
Loadermetadata 常驻，正文按需加载
Governance新增能力先入 inbox，不静默写全局

不是把所有东西自动打开，而是让“启用原因”可见、可回退。

路由器不擅自切能力

如果路由器每轮都擅自切 skill、换 MCP、开插件，短期看起来很主动，长期会变成另一种污染：用户不知道能力为什么进来，也不知道什么时候该退出。V1 的判断很简单：suggest-only，不自动落状态；session attach，不跨项目继承；每次路由都要能解释。

路由器要管住的几个对象

对象建议位置为什么不能少
能力目录.codex/router/catalog.json每个 skill / MCP / plugin / CLI 都要有 scope、category、context_cost、risk_level 和 path，不能靠临场猜。
能力包bundles.tomlfrontend-deai、excel-automation 这类 bundle 手工维护，避免自动归类把能力乱塞。
意图映射intent-map.toml只做高置信规则，且默认 suggest_only，不让一句话直接改全局状态。
会话状态.workspace/skillos/state.json只记录当前 session attach / warm / penalties，不跨线程继承。
路由日志route-log.jsonl / explain-last.json每次建议为什么出现，都要能回看，不靠“系统觉得合适”。
准入区inbox/ → canonical/ → bundles/新能力先审计、分类、确认，再进入正式 catalog。

V1 只建议，不落全局状态

fast-path firstsuggest onlysession attachhuman approve
默认：通用能力足够 → 不触发 bundle
高置信：只建议 attach → 不自动写状态
attach：只对当前 session 有效
detach：用户显式关闭 / 切 bundle / session reset
新增能力：inbox → audit → classify suggestion → human approve → publish

这套原则看起来保守，但它正好防住了能力系统常见的问题：为了省一次确认，把长期上下文污染变成默认状态。
