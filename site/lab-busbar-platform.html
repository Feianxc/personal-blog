先保住旧公式，再谈平台

这种业务最容易卡在个人记忆里：公式在哪、模板在哪、哪个 Excel 该拿来对照，只有当时处理的人清楚；一旦换机器、换人、换线程，就重新掉回找文件、找规则、猜版本的状态。所以这次先把对象和范围固定下来。

材料：parity、构建和公网启动

冻结事实源被正式点名

README 里直接列了 start_sections.json、standard_blocks.json、u_sheet.json、formula_inventory.csv 以及两份关键 Excel。 这说明系统已经承认：平台的地基不是个人记忆里的公式，而是可见、可指认、可保留的事实源。

模块化选择先做表达层，不急着硬造新内核

README 也把范围写得很清楚：当前模块化首先是一种新的选择表达方式，底层仍回落到已验证的 legacy typeCode / block 公式体系。这个判断很重要，因为它说明这次没有为了“更先进”而打断稳定流程。

一键启动流程已经接到公网级别

脚本默认会：
1. 构建前端 dist
2. 启动 uvicorn（127.0.0.1:8002）
3. 启动 Cloudflare Tunnel
4. 写入 pid / 日志到 .workspace/cloudflared/
5. 做本地健康检查

这说明这次不只是在本机“能跑”，而是已经开始考虑别人怎么稳定打开它。

验证命令已经被收成固定动作

python -m pytest tests -q、npm run build、前端 E2E 都在 README 里被写成固定入口。它把“我知道怎么验”改成了“别人也能照着验”。

改规则前的核查对象

还没做完

  • 模块化 busbar 现在先是选择表达层，不是完全自由拼装的新计算内核。
  • 后续新增始端类型或铜排类型，仍要优先基于 analysis_outputs/quickcalc_v3/** 扩展。
  • 本地私有配置仍放在 .workspace/cloudflared/runtime/launcher.settings.json，说明运行环境还没完全产品化。

后续对象

  • 核查冻结事实源和 parity 快照有没有被新需求冲坏。
  • 核查 project-launcher.ps1 的启动流程是否还和当前运行方式一致。
  • 更自由的模块化放在稳定 legacy 体系之后。

留下来的不是“做了个母线平台”这句话，而是 Excel、脚本和记录被收成一套别人回来还能接着跑的东西。
